# 2026.241.0343 — fix(validate): port_relay's socat check used the pre-cutover candy name

## Summary

The `port_relay` soundness rule asks whether the candy shipping the relay wrapper is composed
into a box, and answered it with:

```go
if m.Name == "socat" { hasSocat = true }
```

**That name no longer exists.** `socat` used to live inside charly as `candy/socat`, where the
resolved candy really was named `socat`. It is now the standalone `opencharly/layer-socat`, and a
remote candy is named by its **repo** — the declared node name does not survive a remote scan. So
nothing in a resolved set is named `socat` any more, and the rule fired on every box that composes
the relay **correctly**.

## Root cause, measured

`distro-cachyos`'s three `openclaw` boxes do pull `layer-socat` in, through `pod-openclaw`'s
`require:`. A debug build printing the resolved order shows the candy present and its name
degraded:

```
DBG box=openclaw key="github.com/opencharly/layer-socat" m.Name="layer-socat" view.Name="layer-socat" relayPorts=0
DBG box=openclaw key="github.com/opencharly/pod-openclaw" m.Name="pod-openclaw" relayPorts=1
DBG lookup socat: models=false views=false dk=false
```

The last line is the decisive one: **no candy in the entire project had `Name == "socat"`** — not
in `models`, `views`, or `dk`. The same degradation is visible on the consumer side too
(`pod-openclaw` declares `openclaw:` but resolves as `pod-openclaw`), which is why `hasRelay`
still works: it tests a *field*, not a name.

Two things I checked to rule out simpler explanations before touching the rule:

- **Not a missing reference.** Adding `@github.com/opencharly/layer-socat` directly to the box's
  own `candy:` list did not clear the error either.
- **Not the version skew.** Aligning the refs-list tag to the one `pod-openclaw` requires, and
  removing that refs-list entry entirely, both left the count unchanged at 3.

## The fix

Accept both spellings behind a named predicate — `layer-socat` for the standalone repo, `socat`
for a project that still carries a local socat candy. It is an addition, not a replacement, so
nothing that passes today stops passing.

The predicate stays deliberately narrow. `providesSocatRelay` is a soundness check, so a substring
or prefix match would let a box ship a broken relay silently; the test asserts it rejects
`socat-skill` (layer-socat's *other* entity, which ships no wrapper), `layer-socat-fork`,
`pod-openclaw` (the relay *consumer*), and the empty string.

## How tested

**End-to-end, one binary rebuilt against the same tree:**

```
$ charly box validate            # unpatched plugin-box
box "openclaw":         has port_relay candies but missing "socat" candy
box "openclaw-full":    has port_relay candies but missing "socat" candy
box "openclaw-desktop": has port_relay candies but missing "socat" candy
socat errors: 3

$ charly box validate            # patched plugin-box, same distro-cachyos tree
socat errors: 0
total errors: 0
exit=0
```

`distro-cachyos` now validates **completely clean**, which it has not done in this batch —
these three were the last remaining validation errors after the `plugin-mcp`/`plugin-record`
conflicts were cleared.

**The tests discriminate** — reverting the predicate to the old literal turns them red:

```
$ go test -run TestProvidesSocatRelay ./...      # predicate reverted to `== "socat"`
--- FAIL: TestProvidesSocatRelay_AcceptsThePostCutoverRepoName (0.00s)
    "layer-socat" must satisfy the port_relay rule: post-cutover a remote candy is named
    by its repo, so opencharly/layer-socat resolves as "layer-socat" and never as "socat"
FAIL
```

**Full suite green on the final committed tree** (worktree clean, `-count=1`):

```
$ go vet ./...     # exit 0
$ go test -count=1 ./...
ok   github.com/opencharly/plugin-box/candy/plugin-box   0.005s
```

*Why unit tests on the predicate rather than a fixture build:* the name only degrades on a
**remote** scan, so reproducing the failure through `charly box validate` requires fetching a real
remote candy, which a hermetic test cannot do. The end-to-end proof above is the fixture; these
lock the predicate.
