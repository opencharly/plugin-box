# 2026.288.1356 — fix(workflow)!: name and config-source the readiness probe's bounds (R3)

## Summary

Names and config-sources the two bounds the caller's readiness probe polls on. Today they are unnamed
inline literals:

```js
const deadline = Date.now() + 5 * 60 * 1000;                 // unnamed magic number
await new Promise((r) => setTimeout(r, 20 * 1000));          // unnamed magic number
```

**R3 bans poll-retry and, unconditionally, unnamed magic-number tuning.** Its only stated carve-out is
`exec.Command("podman"/…) where charly is the orchestrator`, which does not apply to a workflow step. They
become named constants supplied through the step's `env`:

```yaml
        env:
          READINESS_WINDOW_MS: "300000"   # 5 minutes: hard deadline for the merge to land
          POLL_INTERVAL_MS: "20000"       # 20 seconds between readiness checks
```

Behaviour is unchanged — the same 5-minute deadline and the same 20-second interval; only the source of
the two values moved, so the bound is auditable configuration rather than an inline number.

**Why this is producer-first**: this caller is copied into 25 repositories, so the violation lives in every
copy. The first successors re-judged against it were blocked with exactly this finding. Correcting the
source is what stops the 26th.

Closes #50
