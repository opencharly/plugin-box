# 2026.241.0005 — fix(validate): the bake_plugin dedupe was directional; the conflict check is not

## Summary

`validateRemoteCandies` compares every remote candy against every other, so it visits a clashing
pair **twice** — `(candy=A, other=B)` and `(candy=B, other=A)`. The `bake_plugin` relationship is
**not** symmetric: only the **baking** repo holds the sibling carrying the ref. Testing one
direction suppressed the visit where the baker happened to be `candy`, and let the mirrored visit
through.

So every baked plugin reported the identical conflict **twice, in opposite orders**. On
`distro-cachyos`:

```
remote candy name conflict: "plugin-mcp"    provided by both …/charly and …/plugin-mcp
remote candy name conflict: "plugin-mcp"    provided by both …/plugin-mcp and …/charly
remote candy name conflict: "plugin-record" provided by both …/charly and …/plugin-record
remote candy name conflict: "plugin-record" provided by both …/plugin-record and …/charly
```

**The duplication was always the tell** — a genuine two-repo clash has no reason to appear in
both orders and a same-provider one has no reason to appear at all.

`charly/candy/charly-mcp` bakes `@github.com/opencharly/plugin-mcp/candy/plugin-mcp`, so `charly`
and the standalone repo are **one provider seen twice** — exactly the case the dedupe exists for.
It simply never fired for the mirrored visit.

## Why the existing test could not catch it

`TestBakePluginSibling` tested the **helper**, in the direction that worked. The **loop** — where
the defect lived — had no test, because it sat behind a network-touching
`loaderkit.CollectRemoteRefsOpts` call that made `validateRemoteCandies` unreachable from a unit
test (passing nils segfaults).

So the loop is extracted into `reportRemoteNameConflicts(candies, e)` — no behaviour change beyond
the fix, and the rule is now reachable without the network prologue.

### The control — the new test fails without the fix

Reverting the dedupe to one direction, **tests unchanged**:

```
--- FAIL: TestBakedPluginConflictIsSuppressedInBothDirections
    baked plugin reported as a conflict: remote candy name conflict:
      "plugin-mcp" provided by both github.com/opencharly/plugin-mcp and github.com/opencharly/charly
```

It fails with **exactly the mirrored message** — the defect's signature, not a generic failure.

`TestGenuineNameConflictIsStillReported` passes in **both** states. That is the guard against the
opposite error: a dedupe that suppresses everything would make the first test pass too, and only
this second one catches it.
