# 2026.294.0021 — fix(validate): reject an image-owned skill, naming the fix (sdk#434 ruling)

## Summary

**The rule.** An image candy (`base:` or `from:`) may not own a `skill:` — the operator ruling on
opencharly/sdk#434, option 3. `charly box validate` now rejects that shape and names the fix.

**Which repo owns the check, and why that one.** `opencharly/plugin-box`. `charly box validate`'s
entire rule engine lives in this repo (the `command:box` plugin), and this repo's own rulebook states
the placement: *"`validate` runs the whole rule engine in-plugin over the resolved-project envelope;
keep new rules there, not in core."* The check is a validate-time ownership rule that needs the raw
config's image set, which the engine has (`cfg.Box`), plus the candy set (`vc.dk`). **Nothing was added
to `opencharly/sdk`**, and candy resolution, `CandyModels`, `ResolvedBoxView` and the CUE schema are
untouched — those are the options the ruling rejected.

**What already existed — stated plainly.** opencharly/sdk#435 replaced a *misleading body-resolution
message* in `deploykit`: for an owner absent from the candy set it said "no SKILL.md exists under
`.agents/skills` beside the owning candy", describing a file search that never runs. That was a
message fix, **not** a rejection of the shape: the node still validated clean whenever it carried an
in-line `content:`, and with no content it produced the wrong explanation. So the shape rule did not
already exist anywhere; what exists is a sharper message one layer down, which this change leaves in
place for the genuinely-unknown owner and stops reaching for the image case (the body walk no longer
sees an image-owned node).

**The exact message** (one line, one finding per node, sorted node order so a migration gate names the
same node twice):

```
skills: skill "psk1": owner "pimage" is an image, not a candy — a `candy:` node carrying `base:` or `from:` folds into the image set, so it has no source directory and this skill's prose can never be read (it is also silently absent from the ai.opencharly.skill label): move this skill to a package candy that the image composes, and set `owner:` to that candy (opencharly/sdk#434)
```

It names the node (`skill "psk1"`) and the `owner:` (`owner "pimage"`), says the `base:`/`from:` node is
an **image, not a candy**, that it has **no source directory**, names the fix verbatim, and cites
opencharly/sdk#434.

**Where the check sits, and why that matters.** `validateSkills` runs the shape stage *before* the body
walk and filters the reported nodes out of the body walk's input, so the shape is reported once, with
the accurate message, whether or not a body exists. The rule fires on the SHAPE only: an image-owned
node carrying an in-line `content:` is forbidden for the same structural reason and **validated clean
(rc=0) before this change** — that is the silent case the ruling turns into an error.

| owner `pimage` is | verdict |
|---|---|
| an image (`base:`/`from:`) | REJECTED with the message above |
| an image **and** a candy (four repos declare one name as both) | accepted — the candy resolves the skill, so the shape is legal |
| neither (a typo'd candy name) | not claimed to be an image; the body walk reports the unresolved owner |
| a package candy the image composes | accepted — the ruling's own fix |

**Step 1 only.** This PR enforces the shape. The re-homing of the 36 affected nodes across 6 repos is
step 2 of the ruling and stays per-repo, tracked by the ruling at opencharly/sdk#434. No repo-root
fallback was added (rejected as #528 option B), and no `SKILL.md` was moved here.

**The R10 witness gained an arm.** `check-box-local` (this repo's disposable `kind:local` validate bed)
now has `box-skill-image-owner`, which asserts the message at the product boundary and whose control —
the same skill re-owned by the package candy the image composes, body beside that candy — must validate
clean, so the arm cannot pass by rejecting everything. It measured **RED on the pre-fix engine** (below).
