# 2026.327.2335 — fix(validate): an INFO-tier skew is not a validation error

## Summary

`charly box validate` turned **every non-warning diagnostic** into a validation error. The verdict
filter skipped only `SeverityWarning`, so `SeverityInfo` fell through, was printed inside
`N validation errors:` and made the command exit 1 — for a candy-version skew the resolver has
**already arbitrated deterministically**.

Two in-tree contracts say that is wrong:

- `sdk/loaderkit/candy_version.go` emits the skew at `DiagInfo`: *"a resolvable skew is INFO, never
  WARNING … a consumer's zero-warnings gate is for unresolved defects and must not fail on a
  successful arbitration."*
- `spec.SeverityError`: *"the only tier a verdict may turn into a non-zero exit."*

The verdict now uses the canonical `Diagnostic.IsError()` predicate (which fails **closed** on an
unknown tier), and info-tier observations are printed as `notice: …` so they stay actionable
rather than merely counted.

## Why this matters (the finding it removes)

Any pin advance that leaves two candies in one box scope naming different tags of the same repo —
the normal shape of a wave — made validate red. Observed while releasing a consumer change:

```
$ charly box validate -C <distro-cachyos checkout>
Notice: candy github.com/opencharly/layer-supervisord resolved to multiple git tags …
Notice: candy github.com/opencharly/pod-ollama resolved to multiple git tags …
charly: error: command "validate": 2 validation errors:
  candy github.com/opencharly/layer-supervisord resolved to multiple git tags …
  candy github.com/opencharly/pod-ollama resolved to multiple git tags …
(exit status 1)
```

Filed as opencharly/charly#1256 with the full trace; this change is its fix.
