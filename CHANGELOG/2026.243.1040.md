# 2026.243.1040 — fix(validate): print the warnings, not just their count

## Summary

`charly box validate` reports `N warnings` and never says what they are.

opencharly/plugin-box#7 made the scan's advisories **countable** by routing them into
diagnostics. But `emitVerdict` skips warning-severity items on the way out:

```go
for _, it := range diags.Items {
    if it.Severity == "warning" {
        continue // the verdict counts ERROR-severity findings
    }
    msgs = append(msgs, it.Message)
}
```

So the summary says `10 warnings, 0 errors` and the operator gets a number with no cause.
**That is worse than the stderr writes it replaced** — those were unstructured, but at least
actionable. A count nobody can act on is not a gate: it says something is wrong and withholds
what.

This is not hypothetical. It was found while trying to clear exactly such a run:

```
charly box validate: OK — checked 494 candies, 38 boxes, 30 deploys, 7 distros, 7 builders; 10 warnings, 0 errors
```

Ten warnings, no way to see any of them, and no flag that lists them.

Warnings now print to **stderr** — stdout stays the machine-readable verdict — and they print
whether or not errors are also present, because a failing run must not hide the advisories
that explain it.

## How tested

```
$ go build ./... && go test ./...
ok  	github.com/opencharly/plugin-box/candy/plugin-box	0.006s
```

**Three guards, each proven to fail without the change.** Negative control — the printing loop
removed, everything else identical:

```
$ go test ./...
--- FAIL: TestEmitVerdictPrintsWarnings
--- FAIL: TestWarningCountMatchesPrintedLines
--- FAIL: TestWarningsPrintedAlongsideErrors
FAIL	github.com/opencharly/plugin-box/candy/plugin-box	0.006s
```

What each pins:

- **warnings reach the operator** — the messages appear on stderr, and warnings alone still
  exit 0, so this cannot turn an advisory into a failure
- **the printed count matches the summary's number** — five warnings in, five `warning: `
  lines out. This is the specific defect: the number must never be the only thing shown
- **warnings survive alongside errors** — an error still produces the verdict error, and the
  advisory is still printed rather than swallowed by it

The guards were written against the failure that motivated the change, not around the
implementation: each asserts what an operator sees, so a future refactor that silently drops
the printing fails them.
