# 2026.282.1752 — fix(validate): check the class vocabulary of plugin.requires: too (supersedes #37)

## Summary

`plugin.providers:` and `plugin.requires:` both name a `#PluginCapability`, but only the `providers:` path had its **class vocabulary** checked. `spec#216` made the CUE pattern's class segment *structural* — so the CUE no longer rejects an undeclared class on either path — which would have left `requires:` with **no vocabulary check anywhere**. This PR moves that check into the one shared reporter, so both paths are covered by one taxonomy (R3) and `requires:` can finally name an undeclared class instead of calling a correct word `malformed`.

**One thing this summary should say out loud, which the reviewer asked for.** `TestPluginCapabilityFaultsAreDistinct` and `TestPluginCapabilityDiagnosticWording` change their fixture from `workflow:lobster` to `zzznotaclass:lobster`. This PR is therefore also **repairing two tests that are red on `main` today** — and the exact colour matters, because an earlier revision of this body described it wrongly:

The fixture did **not** pass vacuously — it went **RED**. `workflow` joined the known class vocabulary (`schema/candy.cue:559`), so the rule correctly stopped reporting a fault for `workflow:lobster`, and every assertion demanding an unknown-class diagnostic began failing. This PR's rename restores a genuinely unknown class and turns both green, and the new bed step asserts that `workflow` *is* in the known set — the same fact from the other side.
