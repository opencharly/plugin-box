# 2026.320.2124 — chore(deps): bump spec to v0.2026320.2116, the release that makes vm fields optional

## Summary

Bumps `github.com/opencharly/spec` from `v0.2026320.857` to **`v0.2026320.2116`**, the release carrying
opencharly/spec#342 — which makes `#ResolvedVm.backend` and `#ResolvedVm.autostart` **optional** and
therefore fixes the org-wide failure of `charly vm create`:

```
charly: error: command "vm": applying vm defaults for "<entity>":
  applyCueDefaults vm: decode: autostart: cannot convert non-concrete value bool
```

Head `693382f`, **2 files, 3 insertions(+), 15 deletions(−)** — `candy/plugin-box/go.mod` and `go.sum`,
nothing else.

**No source change is needed here, and that is verified rather than assumed.** With only the pin moved,
`go build ./...`, `go vet ./...` and `go test ./...` all pass. This module's code already compiles against
the new spec API; it was simply pinned behind it.

### Why this repo, and why it goes first

Bumping `charly` straight to the new spec does **not** work. Measured:

```
$ # charly: spec only
… opencharly/sdk@v0.2026319.1356/deploykit/resolved_project.go:123:40:
  cannot use spec.CandyAlias(a) (value of struct type spec.CandyAlias) as byte value

$ # charly: spec + sdk@v0.2026320.1345
… plugin-box@v0.2026317.2259/inspect_list.go:228:29: a.Name undefined (type by…)
```

So the order is **spec → plugin-box → charly**, and the middle link is this PR. And the wave is small
rather than an org-wide sweep: enumerating the failing modules in `charly`'s build graph yields exactly
**one** —

```
$ go build ./... 2>&1 | grep -oE 'opencharly/[a-z0-9-]+/candy/[a-z0-9-]+@v[0-9.]+' | sed 's#@.*##' | sort -u
opencharly/plugin-box/candy/plugin-box
```

`charly`'s consumer commit follows once this is tagged.


this tag **and** the `charly` consumer bump that follows it. This PR does not claim it.
